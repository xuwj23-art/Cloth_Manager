## 1. 项目背景与目标

面向**小型服装零售商铺**的进销存 App，核心能力：

- **仓库端**：给每个 SKU 服装拍照建档，标注尺码、颜色、库存、价格，并生成 QR 吊牌。
- **店铺端**：用手机摄像头扫描 QR 吊牌，**自动匹配出该服装全部信息**。
- **销售出库**：扫码即出单，售出后**实时同步扣减库存**。

## 2. 目标用户与场景画像

| 维度 | 描述 | 对设计的影响 |
|------|------|-------------|
| 商铺规模 | 小型商铺（1～5 人），非工厂/品牌 | 轻量、低成本、单店或少量门店 |
| 货品特征 | **杂款为主**（款多、单款量少、上新快） | SKU 多、生命周期短 → 必须**极速建档** |
| 硬件预算 | 有限，用手机当扫描设备 | 手机摄像头扫码为主，蓝牙设备为可选 |
| 操作人员 | **零基础**，不熟悉复杂软件 | 流程极简、按钮大、少输入、防错 |
| 网络环境 | 仓库/店铺信号可能不稳 | **离线优先**，联网后自动同步 |
| **开发者（你）** | **软件零基础，依赖 AI 开发** | 技术栈与流程要**AI 友好、单一语言、强约束** |

> **杂款** 本质是「高 SKU 数 + 低单款库存 + 高周转」→ 决定了：图像识别难奏效、建档速度是核心、QR 唯一码匹配最稳。

## 3. 技术路线与技术栈选择（核心调整）

### 3.0 为什么是路线 A（QR 吊牌）而非图像识别
| 对比项 | 路线 A：QR 吊牌 ✅ | 路线 B：图像识别 |
|--------|------------------|-----------------|
| 准确率 | 接近 100% | 杂款下偏低 |
| 速度 | 毫秒级、可离线 | 慢、依赖算力/网络 |
| 成本 | 低、成熟 | 高、需训练维护 |
| 杂款适配 | 完美 | 差（样本少） |
| 零基础+AI 实现难度 | 低 | 高 |

### 3.1 前端框架：推荐 React Native (Expo) + TypeScript

> 这是对 v1.0「Flutter」推荐的**修正**，原因是你的两个新约束：零基础 + 大量用 AI。

| 维度 | React Native(Expo)+TS ✅ 推荐 | Flutter(Dart) 备选 |
|------|------------------------------|-------------------|
| 与后端语言统一 | **同为 TypeScript，全栈一种语言** | 前端 Dart、后端 TS，两种语言 |
| AI 生成质量 | 训练语料最大，AI 产出最准、报错好搜 | 语料较少 |
| 学习成本（你） | 只学一门 TS | 需额外学 Dart |
| 前后端共享模型 | **可共享类型/校验，AI 上下文更完整** | 不能共享 |
| 性能/稳定 | 本应用（表单+扫码+列表）完全够用 | 略优，但本场景差距可忽略 |
| 扫码能力 | `expo-camera` / `vision-camera` 成熟稳定 | 成熟 |

**结论**：选 **React Native + Expo + TypeScript**。本 App 不是高强度图形应用，RN 性能足够；而「全栈统一 TypeScript」对零基础 + AI 开发是决定性优势。

### 3.2 后端框架：确定 NestJS（TypeScript）

> 你给的选项是 NestJS 或 Go，最终选 **NestJS**。

| 维度 | NestJS(TS) ✅ | Go |
|------|--------------|-----|
| 与前端统一语言 | **是（全栈 TS）** | 否 |
| AI 友好度 | 极高（语料多、结构化框架） | 中 |
| 框架完备度 | 内置鉴权/校验/ORM/模块化，开箱即用 | 需自行组装较多 |
| 零基础上手 | 约定式结构，AI 容易遵循 | 偏底层 |
| 性能 | 对本业务量足够 | 更高（本场景用不到） |

**结论**：**NestJS + TypeScript**。配合前端 RN，实现「**一种语言贯穿全栈**」，最大化 AI 效率与你的可掌控度。

### 3.3 最终技术栈总览

| 层 | 选型 | 说明 |
|----|------|------|
| 移动端 | **Expo (React Native) + TypeScript** | 双端一套码；扫码 `expo-camera` |
| 本地数据库 | SQLite（`expo-sqlite` / WatermelonDB / Drizzle） | 离线优先 |
| 状态管理 | Zustand / TanStack Query | 简单稳定，AI 易写 |
| 后端 | **NestJS + TypeScript** | 自建 REST API |
| ORM | Prisma | 类型安全、AI 友好、迁移方便 |
| 主数据库 | PostgreSQL（托管） | 关系型，稳定 |
| 缓存/队列 | Redis（可后置） | 限流/会话/异步 |
| 图片存储 | 对象存储（阿里云 OSS / 腾讯云 COS / 七牛 / Cloudflare R2） | 不入数据库 |
| 代码组织 | **pnpm Monorepo（Turborepo）** | 前后端 + 共享类型同仓，AI 上下文完整 |
| 部署 | PaaS（Railway / Render / Fly.io 或 国内云容器） | 零基础免运维 |
| 监控 | Sentry（崩溃/错误）+ 日志 | 生产可观测 |

## 4. 产品设计原则

1. **离线优先**：核心操作无网也能做，先落本地再后台同步。
2. **三步内完成**：卖一件衣服 ≤ 3 步操作。
3. **少输入、多选择**：尺码/颜色/品类用预置选项与模板。
4. **防错优于纠错**：库存为 0 禁出库、重复扫码提示、删除二次确认。
5. **快即是稳**：扫码出结果 < 1 秒；冷启动 < 2 秒。

## 5. 核心功能模块

### 5.1 商品建档（仓库端）
- 拍照（封面必填，1～3 张）。
- 录入品名、品类、**颜色 + 尺码（多选生成多 SKU）**、进价、售价、初始库存。
- **批量生成 SKU**：选「红/蓝」+「S/M/L」→ 自动生成 6 个 SKU。
- 每个 SKU 自动分配唯一编号并生成 QR。
- **款模板**：常用尺码组/品类一键带入，加速杂款上新。

### 5.2 QR 吊牌管理
- 生成 QR（内容仅含唯一 SKU 编号，业务信息从库里取）。
- 对接蓝牙标签打印机打印吊牌（可选）。
- 无打印机时支持绑定/读取现有吊牌条码（兼容 Code128/EAN）。

### 5.3 扫码匹配（店铺端）
- 手机摄像头扫 QR（或蓝牙扫码枪）。
- 扫到弹出商品卡片：图片、品名、尺码、颜色、售价、**实时库存**。
- 本地库优先匹配，毫秒级。

### 5.4 销售开单与出库
- 扫码 → 购物车 → 选数量 → 结算 → **自动扣库存**。
- 支持改价/折扣（按权限）。
- 生成销售单（时间、操作人、金额）。

### 5.5 库存管理
- 实时库存、低库存预警。
- 入库/出库/盘点/调拨（多门店为远期）。
- 库存流水可追溯。

### 5.6 数据与报表
- 销售流水、每日营业额、热销/滞销款。
- 商品搜索与筛选（品类/颜色/库存状态）。

### 5.7 用户与门店
- 角色：老板（管理员）/ 店员。
- 权限：店员默认不可改进价、不可删除。
- 多门店分仓（远期）。

## 6. 关键业务流程

### 6.1 仓库建档
```
新增商品 → 拍照 → 选品类(模板) → 选颜色+尺码(多选)
 → 批量生成 SKU → 填进价/售价/库存 → 保存 → 生成 QR → (可选)打印吊牌
```

### 6.2 店铺销售（最关键路径）
```
打开App(默认进收银扫码页) → 扫 QR → 弹商品卡片
 → 加入(默认数量1) → 结算 → 库存自动-N + 生成销售单
```
> 全程 ≤ 3 步。

### 6.3 离线同步
```
操作 → 写本地 SQLite + 写同步队列
 → 有网络 → 后台按队列上传
 → 服务端按「op_id 幂等 + version 乐观锁 + 流水重放」合并
 → 拉取他端变更 → 更新本地
```

## 7. 数据模型（核心表）

> SKU = 款 + 颜色 + 尺码 的唯一组合，是库存与 QR 的核心键。

### 7.1 商品款 Product(SPU)
`id, name, category_id, cover_image, images(json), shop_id, created_at, updated_at`

### 7.2 SKU
`id, product_id, color, size, barcode(唯一/QR内容), cost_price, sale_price, stock, version`

### 7.3 库存流水 StockMovement
`id, sku_id, type(in/out/adjust/transfer), quantity(带正负), ref_order_id, operator_id, op_id(幂等), created_at`

### 7.4 销售单 SaleOrder + 明细 SaleItem
- 单：`id, shop_id, operator_id, total_amount, status, created_at`
- 明细：`order_id, sku_id, quantity, price, subtotal`

### 7.5 其他
`User, Shop, Category, SyncQueue`

> 用 **Prisma schema** 定义这些模型，AI 可据此自动生成迁移、类型、CRUD。

## 8. 技术架构

```
┌─────────────────────────────┐
│   移动端 App (Expo / RN, TS) │
│  UI/业务 → 本地SQLite → 同步引擎 │
└───────────┬─────────────────┘
            │ HTTPS REST (JWT)
┌───────────▼─────────────────┐
│   后端 NestJS (TS)           │
│  鉴权 / 商品·库存·订单服务    │
│  同步与冲突合并 / Prisma ORM  │
└───────────┬─────────────────┘
   ┌─────────▼────────┐  ┌──────────────┐
   │ PostgreSQL(托管) │  │ 对象存储(图片) │
   └──────────────────┘  └──────────────┘
            │
        Sentry 监控 / 日志 / 备份
```

### 8.1 Monorepo 项目结构（AI 友好的关键）
```
cloth_scan/
├─ apps/
│  ├─ mobile/      # Expo (React Native) App
│  └─ server/      # NestJS 后端
├─ packages/
│  └─ shared/      # 共享：类型、Zod 校验、常量、DTO
├─ docs/           # 方案与规格文档（本文件所在）
├─ package.json    # pnpm workspace
└─ turbo.json
```
> 前后端共享 `packages/shared` 的类型与校验，让 AI 在任一端都有完整上下文，减少前后端不一致的 Bug。

### 8.2 离线同步与冲突处理（稳定性核心）
- 写操作先本地成功，进入**同步队列**。
- 库存用**增量流水累加**而非覆盖绝对值，避免并发写错。
- 每条操作带客户端生成 `op_id` → **幂等**，重复上传不重复扣减。
- 冲突以服务端为权威，`version` 乐观锁 + 流水重放合并。

## 9. QR 吊牌方案细节
- **编码**：QR 为主（手机识别快、抗污损、容错高）；兼容读取现成 Code128/EAN。
- **内容**：仅存「全局唯一 SKU 编号」，业务信息从数据库取（保证可更新）。
- **编号规则**：门店前缀 + 雪花/自增 ID，全局唯一、防重复。
- **打印**：对接蓝牙热敏标签机；无打印机时绑定现有吊牌。

## 10. AI 辅助开发工作流（针对零基础的你 —— 重点章节）

目标：**让 AI 承担绝大部分编码，你负责理解、决策、验收**。为此做了如下设计。

### 10.1 选型即为 AI 优化
- **全栈单一 TypeScript**：AI 产出最准、你只学一门语言。
- **约定式框架（NestJS）+ Prisma + Zod**：结构强约束，AI 不易跑偏。
- **Monorepo + 共享类型**：AI 有完整上下文，前后端不脱节。

### 10.2 文档/规格驱动开发（Spec-Driven）
- 每个功能先写一份**简短规格**（输入、输出、界面、验收标准），放 `docs/specs/`。
- 让 AI 按规格实现，再按「验收标准」逐条检查。
- 本方案文档即「总规格」，后续每模块再拆小规格。

### 10.3 小步快跑 + 守护栏
- 任务拆成「能在一两次对话内完成」的小块。
- **自动化测试当守护栏**：核心逻辑（库存扣减、同步幂等）必须有单元测试，AI 写完即跑，防止改坏。
- **类型 + 校验（Zod）**：编译期与运行期双重防错。

### 10.4 你的工作节奏（建议）
1. 用自然语言描述要做的功能（参照规格模板）。
2. 让 AI 实现 + 写测试。
3. 在手机/模拟器上**实际点一遍**验收。
4. 有问题把报错原文贴给 AI 修。
5. 阶段性让 AI 做**代码审查与重构**，保持可维护。

### 10.5 免运维优先（降低你的负担）
- 部署用 **PaaS（Railway/Render/Fly.io）**：连 Git 自动构建上线，无需懂服务器。
- 数据库用**托管 PostgreSQL**（自带备份）。
- 图片用对象存储；错误用 **Sentry** 自动上报。
- 这些都能让 AI 帮你配置，且极少需要你手动运维。

## 14. 成本、风险与中国大陆落地

### 14.1 成本
- 云服务：PaaS + 托管 PostgreSQL + 对象存储（小规模月成本可控，按量计费）。

- 硬件（用户侧可选）：蓝牙扫码枪、标签打印机。

### 14.2 风险与对策
| 风险 | 对策 |
|------|------|
| 离线同步导致库存错乱 | 流水累加 + 幂等 + 版本号；重点测试 |
| 零基础 + 生产级有难度 | 选型 AI 友好 + 免运维 PaaS + 测试守护栏 + 小步验收 |
| 杂款建档慢 | 模板 + 批量 SKU + 最少输入 |
| 用户上手难 | 首页即收银、新手引导、可用性走查 |
| 安全/数据合规 | 不自行存敏感支付信息；用成熟鉴权；依赖扫描 |

### 14.3 中国大陆落地注意事项（开发主体：个体户）
- **主体资质**：以**个体户营业执照**作为开发者/备案主体，多数环节够用。建议提前办好执照与对公/经营者账户。
- **ICP 备案**：自有域名 + 国内云需备案，个体户可作为备案主体（部分省份对个体户备案有具体要求，按所在地通管局规定办理）。
