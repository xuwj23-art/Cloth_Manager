# 分尺码数量管理与条码打印区分 · 调研方案

> 状态：**调研稿（待确认后实施）**
> 日期：2026-09-01
> 需求来源：店主提出「同一货品的不同尺码可以分别编辑数量，并明确不同尺寸的打印条码如何管理区分、打印界面如何适配」。
> 本文为第一轮交付物：现状结论 + 实现方案 + 分期建议，**不包含代码改动**。

---

## 1. 结论速览（TL;DR）

1. **数据模型天然支持分尺码管理**——条码、库存、销售明细全链路本来就是 SKU（颜色×尺码）粒度，不需要任何数据库迁移。
2. **编辑商品页已经能逐 SKU（即逐尺码）改库存**（owner 权限），只是入口较深、staff 无权限；真正的缺口在**建档页**：目前所有 SKU 共用一个「库存」输入。
3. **条码体系建议维持现状**（每 SKU 一条全局唯一的 10 位随机数字码）。「人眼区分不同尺码的吊牌」不该靠改编码规则解决，而应该**把颜色/尺码文字印到标签上**——成本低一个量级且不动存量数据。
4. 打印界面已有按 SKU 的卡片与份数控制，缺的是**标签上的规格文字**和**分组视图/快捷填充**等易用性增强。

---

## 2. 现状调研（附代码证据）

### 2.1 条码：每 SKU 全局唯一、随机、不可变

| 事实                                                                              | 位置                                                                                          |
| --------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 生成规则：10 位纯随机数字（首位非 0，便于手输），批内去重 + 查库排重 + P2002 重试 | `apps/server/src/products/products.service.ts` `genNumericBarcode` / `generateUniqueBarcodes` |
| 唯一性由 DB 强制：`barcode String @unique`（跨门店全局唯一）                      | `apps/server/prisma/schema.prisma` `Sku` 模型                                                 |
| 条码不可改：`UpdateSkuInput` 无 barcode 字段，注释「不增删 SKU，条码不变」        | `packages/shared/src/product.ts`                                                              |
| 建档可手填已有吊牌条码（绑定存量吊牌），留空才自动生成                            | `CreateSkuInput.barcode` optional                                                             |
| 标签打印内容 = 二维码（内容即 barcode）+ 一行条码数字；**无颜色/尺码/价格文字**   | `apps/mobile/src/printer/labelLayout.ts`（注释明确「标签不含价格」）                          |

**含义**：同一商品不同尺码 = 不同 SKU = 不同条码，体系上早已「天然区分」。已印吊牌永久有效（条码不变）。

### 2.2 库存与销售：全链路 SKU 粒度

- 库存唯一真相是 `StockMovement` 流水（in/out/adjust），`Sku.stock` 是物化结果；`SaleItem` 挂 `skuId`，销售按 SKU 扣减。
- 手机端本地缓存 `skus_cache` 以 barcode 为主键、一行一 SKU；扫码收银精确等值匹配到单个 SKU（`apps/mobile/src/db/catalog.ts`、`CashierScreen.lookupAndPrompt`）。
- **同步**：`GET /products/sync` 增量拉取 + 逐 SKU `INSERT OR REPLACE`，无聚合逻辑。

**含义**：「不同尺码分别管理数量」不需要新建任何模型/接口。

### 2.3 数量编辑的现状

| 场景              | 现状                                                                                                | 位置                                                                                          |
| ----------------- | --------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 建档              | ❌ 所有 SKU 共用一个「库存」输入（默认 1），`expandSkuMatrix` 的 `initialStock` 是标量              | `CreateProductScreen.tsx`（价格与库存卡）+ `packages/shared/src/product.ts` `expandSkuMatrix` |
| 编辑商品（owner） | ✅ 每个 SKU 卡片有独立「库存」输入，保存时按目标值写 `adjust` 流水（差额），并触发售罄归档/补货恢复 | `EditProductScreen.tsx`「规格 · 会员价 · 库存」卡 + `products.service.ts` updateProduct       |
| 编辑商品（staff） | ❌ 编辑页 owner 专属（`@Roles("owner")`），店员只读                                                 | PRD 权限矩阵                                                                                  |
| 独立盘点入口      | 无（盘点语义就是编辑页改库存）                                                                      | —                                                                                             |

**注意**：建档后想改某个尺码的数量，现在就能做——进「编辑商品」逐 SKU 改库存。所以「分别编辑数量」的**主要缺口是建档时**，其次是编辑入口的易用性/权限范围。

### 2.4 打印界面现状

- 入口唯一：商品列表 → 编辑商品（非编辑态）→「打印吊牌二维码」→ LabelPrint 屏，一次一个商品。
- 粒度已按 SKU：每个 SKU 一张卡片（QR 预览 + 名称/颜色尺码/库存/会员价 + 独立份数步进器），右上「按库存」一键把份数填成库存数。
- 蓝牙打印 `buildCtPrintJob(product, qtyBySku, …)`：每 SKU 生成 `{ qr, copies, texts:[条码数字] }`；PDF 分享路径（Expo Go 降级）同样只有 QR + 数字。
- **缺口**：打出来的吊牌上只有码和数字，店员肉眼无法区分「红 M」和「红 L」，只能记随机数字或扫码确认。

## 3. 实现方案

### 3.1 建档时逐尺码分别填数量（核心缺口）

**后端零改动**：`CreateSkuInput.initialStock` 本来就按 SKU 接收，`createProduct` 已逐 SKU 写 `in` 流水。改动集中在 shared 纯函数 + 建档 UI。

#### shared 改造（保持向后兼容）

`expandSkuMatrix` 增加可选参数（现有调用不破坏）：

```ts
expandSkuMatrix(params: {
  colors: string[];
  sizes: string[];
  costPrice: number;
  salePrice: number;
  initialStock?: number;                    // 现状：所有 SKU 共用
  initialStockBySize?: Record<string, number>; // 新增：按尺码给量（同码所有颜色共享）
})
```

> 是否需要「颜色×尺码」二维矩阵（Record<color, Record<size, n>>）？调研判断**不需要**：小服装店同款不同颜色进货量通常一致或按色批量，二维矩阵会把建档界面变成大表格，违背「快建档」的核心场景。真有按色差异的，建档后到编辑页微调。

#### UI 方案对比

| 方案                               | 形态                                                                           | 优点                                                         | 缺点                             |
| ---------------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------ | -------------------------------- |
| **A. 尺码行数量输入（推荐）**      | 选完尺码后，尺码区下方渲染「每码一行：尺码名 + 数量输入/步进」，实时汇总总库存 | 界面简单、纵向排布不挤；符合“S 进 3 件、M 进 5 件”的口述习惯 | 不能按颜色区分数量               |
| B. 颜色×尺码网格                   | 二维表格逐格填                                                                 | 最灵活                                                       | 界面重、建档变慢；手机窄屏体验差 |
| C. 统一库存 + 「逐码填写」展开开关 | 默认现状（一个数），点开关展开成方案 A                                         | 兼顾快与细，学习成本低                                       | 多一层交互                       |

**推荐 A（直接做成默认）**：把现有「价格与库存」卡里的库存输入**挪到尺码区内**，每选一个尺码自动生成一行（默认 1），取消勾选尺码则行移除。价格区只剩进价/会员价，界面反而更清爽。总库存显示 `共 N 件` 于尺码区标题右侧。

#### 交互细节

- 尺码行：`[M] [ − 1 ＋ ]` 或直接数字输入框（推荐步进器，单手快）；长按数字可直接键入。
- 汇总：`尺码 (共 12 件)`。
- 识图建档（AI 路径）默认每码 1，进入手动确认后可改。

### 3.2 编辑已有商品的逐尺码数量

**现状已支持**（owner），建议只做易用性增强（可选，非必须）：

- 非编辑态的 SKU 只读行已显示库存；可在只读态顶部加「总库存 N · K 个规格」汇总行（编辑态已有）。
- **店员盘点权限**：PRD 权限矩阵店员不能编辑商品（含库存）。若业务上需要店员盘点，属于产品决策变更（建议单独立项，后端 `@Roles("owner")` 与前端入口同步放开，并考虑流水 operatorId 审计）。本文不默认实施。

### 3.3 同商品不同尺码的条码管理策略

| 方案                                                                     | 说明                   | 评估                                                                                                                                                              |
| ------------------------------------------------------------------------ | ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **维持：每 SKU 唯一 10 位随机数字码（推荐）**                            | 现状                   | ✅ 零迁移；唯一性 DB 强制；条码不变=已印吊牌永久有效；不泄露 SKU 规模 ❌ 人工看码无语义（用 3.4 标签印规格文字补足）                                              |
| 语义化编码（款号+色码+尺码，如 `P0001-BLK-M` 或纯数字段式 `1001 01 03`） | 人眼可读、电话核对方便 | ❌ 存量条码不能变（吊牌已发）→ 新旧并存两套规则；需要款号序列生成器；位数变长手输更累；泄露经营规模；与「手填已有吊牌条码」特性冲突。**除非店主强烈要求，不建议** |

**结论**：维持随机码。「区分」交给标签内容（3.4）与屏幕界面（3.2/3.4），不改编码体系。

补充：若未来出现「同一尺码想复用同一张吊牌」的需求（如均码散卖），可在 SKU 建档时手填同一 barcode——但当前 DB `@unique` 不允许共用，且会破坏「一码一 SKU」的扣库存语义，**不建议开这个口子**。

### 3.4 标签可区分性：把「颜色 尺码」印上吊牌

这是本调研中**性价比最高的改动**，直接解决“打出来的吊牌分不清尺码”。

#### 排版方案（60×40mm 默认版）

现状：QR 居中 + 底部一行条码数字，已接近占满。两案：

- **案 1（推荐）：文字加在条码数字行**——把底部一行拆成两行小字：`红 M`（scale 1，稍大）+ 条码数字（scale 1）。QR 略上移/缩 1~2mm 即可腾出空间。改动小，40×30 小标签同样适用（小标签可只印规格、省略数字行——但会失去手输兜底，默认保留）。
- 案 2：QR 左置 + 右侧竖排规格与数字。可读性最好，但 portrait/4 种尺寸都要重排，工作量大，作为备选。

实施要点：

- `labelLayout.ts` 的 `CtLabel.texts` 增加规格行（`${color} ${size}`，均码可只印颜色）；landscape/portrait 两个分支都要改。
- PDF 降级路径 `buildLabelsHtml`（LabelPrintScreen）同步加规格文字，保持两条路径一致。
- **必须真机试打校准**：203dpi 与 300dpi、4 种可选尺寸都要试；建议先在预览界面渲染出与实物 1:1 的示意图供确认。
- 规格文字来源 `product.skus` 的 color/size，无侵入。

#### 打印界面适配（易用性）

- SKU 卡片**按颜色分组**展示（同色分块 + 组头「红色 · 3 码」），扫一眼即知一色几码。
- 份数快捷：「按库存」保留；增加「每码 1 张」（新上架逐码挂样的常见场景）。
- 二期：商品列表多选 → 批量打印（入口从「编辑商品」内移出/复制一份到列表），需要新的路由参数与聚合视图。

## 4. 分期实施建议

| 期                         | 内容                                                    | 量级                                         | 分发       |
| -------------------------- | ------------------------------------------------------- | -------------------------------------------- | ---------- |
| **P1**                     | 建档逐尺码数量（方案 A）+ 标签印「颜色 尺码」+ PDF 同步 | shared 函数 + 2 个屏 + 排版微调，约半天~1 天 | 全 JS，OTA |
| **P2**                     | 打印界面按颜色分组、每码 1 张快捷、预览 1:1 示意        | 1 屏内改动                                   | OTA        |
| **P3（可选，需产品决策）** | 店员盘点权限放开；商品列表批量打印入口                  | 涉及权限矩阵与后端守卫                       | 需重审 PRD |

## 5. 风险与注意

1. **标签排版必须真机验证**（不同 dpi/纸型），P1 合入前先试打一版样张给店主确认。
2. `expandSkuMatrix` 新参数保持 optional，向后兼容旧调用与既有测试。
3. 条码数字行不建议从小标签（40×30）上拿掉：扫码枪识别失败时「手输条码」是唯一兜底。
4. 若实施 3.1 方案 A，「价格与库存」卡片信息密度下降，注意建档页滚动长度变化（尺码行增多），必要时尺码行做紧凑模式（高 40dp 内）。

## 附：与本调研相关的已落地改动（2026-09-01 同批）

- 尺码预设已改为三组（字母码/女装码/裤装码）+ 均码，建档页分组展示——见 `packages/shared/src/catalog-presets.ts` `PRESET_SIZE_GROUPS`。本文 3.1 的「尺码行数量输入」直接在该分组区下方展开即可。
- 商品「售价」已更名「会员价」（salePrice 即会员价/实价），原价为推导值不落库——打印界面卡片文案已同步「会员价 ¥X」。
